# Supabase Foundation Implementation Plan

> **Execution rule:** Use this plan one Task at a time. Finish the Task's minimum verification, commit it independently, then stop for human review before starting the next Task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an optional, non-blocking Supabase account foundation to Toss: reproducible local infrastructure, secure account tables, native Sign in with Apple, session restoration, profile/preference sync, account settings, logout, and in-app deletion, while preserving the existing offline Toss experience.

**Architecture:** `TossApp` constructs an `AppDependencies` graph and renders the existing coin experience immediately. One shared `AppEnvironment` owns a serialized `SupabaseClientGenerationProvider`; every live account dependency uses its one current active client/storage generation, while retired generations remain permanently unable to mutate the Session. Account state runs independently through protocol-backed services and repositories. PostgreSQL owns account records and RLS, Supabase Auth owns Apple identities, and a JWT-protected Edge Function is the only privileged account-deletion path.

**Tech Stack:** iOS 17.5, SwiftUI, MVVM, AuthenticationServices, Supabase Swift 2.x through Swift Package Manager, Supabase CLI, PostgreSQL, pgTAP, Supabase Edge Functions/Deno, XCTest.

## Global Constraints and Stable Interfaces

- Keep `IPHONEOS_DEPLOYMENT_TARGET = 17.5`.
- Do not alter `ContentView`, RealityKit/USDZ loading, gesture/motion/result state, Haptic timing, or WAV behavior except the narrow preference enable/disable hooks in Task 6.
- `AppRootView` renders `ContentView()` immediately. Session restoration and sync run in an independent `Task`; Toss never awaits network work.
- Supabase Swift 2.49.0 starts its internal Auth event listener when `SupabaseClient` is constructed. The resulting initial-session flow can load a persisted local session and refresh it when necessary. This accepted SDK background behavior must never gate `AppRootView`, the guest experience, or any Toss interaction.
- The App owns one shared `AppEnvironment` and, at any instant, exactly one active `SupabaseClientGeneration`. All live dependencies resolve that same current generation through `SupabaseClientGenerationProvider`; no global mutable Supabase singleton exists.
- Each generation binds one `SupabaseClient` to one `GenerationBoundAuthLocalStorage` and one immutable epoch. Rotating generations atomically retires the old generation before activating the new one. A retired generation permanently rejects Session stores and cannot be reopened.
- SDK refresh work can outlive sign-out. Store operation IDs protect UI state only; generation retirement is the mandatory persistence boundary that prevents an old client from rewriting the current Keychain Session. Old client operations and auth events must be rejected by the same generation epoch.
- Guests are local-only users, not Supabase anonymous Auth users. Default coin use never creates an account.
- Client configuration contains only `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, injected per build configuration.
- Supabase secret/service-role keys, Apple `.p8`, Apple client secrets, database passwords, access tokens, and refresh tokens never enter the app, Git, logs, fixtures, or example values.
- Supabase Auth `identities` owns Apple subjects. No business table stores `apple_subject`.
- Each executable task starts with a failing focused test, ends with scoped verification, and has one English commit.
- Execute exactly one Task per implementation session. After its minimum verification and independent commit, stop for human inspection.
- Do not repeat the full build or the original 39-test suite for every small step. Run them only after package/project dependency changes, at major integration gates explicitly listed below, and in Task 9.
- The verified simulator destination is `platform=iOS Simulator,name=iPhone 15 Pro,OS=17.5`. If unavailable, run `xcrun simctl list devices available`, report compatible iOS 17.5 devices, and do not alter the deployment target.

    let url: URL
    let publishableKey: String
    static func load(from bundle: Bundle) throws -> Self
}

enum AccountSession: Equatable, Sendable {
    case guest
    case restoring
    case authenticated(userID: UUID)
}

enum ServerSessionRevocation: Equatable {
    case revoked
    case deferred
}

struct SupabaseClientGenerationID: Hashable, Sendable {
    let rawValue: UUID
}

enum AccountAuthEventKind: Equatable, Sendable {
    case initialSession
    case signedIn
    case signedOut
    case tokenRefreshed
}

struct AccountAuthEvent: Equatable, Sendable {
    let generationID: SupabaseClientGenerationID
    let kind: AccountAuthEventKind
    let session: AccountSession?
}

enum SupabaseClientGenerationLifecycle: Equatable, Sendable {
    case active
    case retiring
    case retired
}

protocol SupabaseClientGenerationProviding: Sendable {
    func current() async throws -> SupabaseClientGeneration
    func rotate() async throws -> SupabaseClientGeneration
    func retireCurrent(expectedID: SupabaseClientGenerationID) async throws
    func isCurrent(_ generationID: SupabaseClientGenerationID) async -> Bool
}

struct AppleSignInCredential: Equatable {
    let identityToken: String
    let authorizationCode: String
    let rawNonce: String
    let displayName: String?

@MainActor
protocol AppleSignInServicing {

protocol UserProfileRepository {
    func fetch(userID: UUID) async throws -> UserProfile

## Task 8: Implement Secure In-App Account Deletion

**Create:** deletion-request migration/test, function env example, shared TypeScript files, Edge Function/test, iOS deletion protocol/service/view, dedicated iOS tests.

**Inputs/outputs:** Client first completes native Apple reauthentication and refreshes its Supabase session, then sends `{ authorizationCode, requestID }`. Success is HTTP 200 with `{ deleted: true, requestID, appleRevocation: "revoked" | "already_invalid" | "manual_required" }`. Stable failures are limited to 401 invalid/stale Supabase reauthentication, 422 identity mismatch, and 500 Toss/Supabase data deletion failure. Apple revocation failure is not a data-deletion failure.

`account_deletion_requests` has exactly `request_id uuid primary key`, checked `status text`, `requested_at timestamptz`, nullable `completed_at timestamptz`, and checked `apple_revocation_status text`. - [ ] XCTest: fresh Apple reauth required, cancellation harmless, stable request ID retry, success returns guest.

**Minimal implementation**

- [ ] Create `account_deletion_requests` with status values `requested`, `processing`, and `completed`; Apple status values are `pending`, `revoked`, `already_invalid`, and `manual_required`. Enable and force RLS, revoke anon/authenticated access, and permit access only to the server client.
- [ ] Define transitions: first call inserts `requested/pending`; a worker atomically claims it as `processing`; Toss deletion success sets `completed`, `completed_at`, and the final Apple status. A retry of `requested` or a recoverable stale `processing` row resumes work. A retry of `completed` returns its stored terminal response without another revoke/delete call. - [ ] Compare the recent Supabase-authenticated Apple identity and, when token exchange succeeds, the returned Apple subject to the caller's current Apple identity.
